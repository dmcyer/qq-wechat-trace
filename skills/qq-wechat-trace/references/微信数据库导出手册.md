## 1. 快速路径

### 1.1 解密任意库并读消息（三步，微信无需运行）

```python
# ① 从 tar 提取（含 wal/shm）
import tarfile, os, sqlcipher3, json, datetime
WORK = r'<home>/work/from_backup'
member = '<WX_ACCOUNT>/db_storage/message/message_6.db'   # 换成你要的库
with tarfile.open(r'D:\wx_db_backup_<日期>_db_storage.tar') as tf:
    for n in tf.getnames():
        if n.startswith(member): tf.extract(n, WORK)
src = os.path.join(WORK, member)

# ② 密钥打开（★外层双引号；page_size 在 key 前）
info = json.load(open(r'keys/wx_db_key_map.json', encoding='utf-8'))['message\\message_6.db']
con = sqlcipher3.connect(src, isolation_level=None)
con.execute("PRAGMA cipher_page_size = 4096;")
con.execute('PRAGMA key = "%s";' % ("x'%s%s'" % (info['key'], info['salt'])))

# ③ 读消息——★文本消息的 message_content 直接是明文，无需 protobuf
rows = con.execute('SELECT create_time, message_content FROM "Msg_xxx" WHERE local_type=1 ORDER BY local_id').fetchall()
def ts(t): return (datetime.datetime.utcfromtimestamp(t) + datetime.timedelta(hours=8)).strftime('%Y-%m-%d %H:%M:%S')
for t, c in rows: print(ts(t), c)
```

### 1.2 找会话的 Msg 表

`Name2Id` 表：用户名（wxid / `xxx@chatroom`）→ 表序号；每个聊天一张 `Msg_<32位hash>` 表。群名在 `contact.db` 的 `contact` 表（`username LIKE '%@chatroom'` → `nick_name`）。

**⭐ Msg 表名 = `md5(用户名)`**（实测验证）：
```python
import hashlib
table = 'Msg_' + hashlib.md5('<群号>@chatroom'.encode()).hexdigest()
```

### ⭐ 发送者解析（2026-09-22 实测，容易搞错）

**群消息的 `message_content` 有 94% 自带发送者前缀**：`"发送者wxid:\n正文"`。正确做法：
1. 先剥前缀 `^([A-Za-z0-9_\-@\.]{1,64}):[ \t]*\n` → 发送者 = 该 wxid（经 contact.username/alias → nick_name 映射）
2. **不要用 `real_sender_id` → contact.id 映射**（实测对不上，会把发送者张冠李戴）
3. 无前缀的消息（约 6%）是本人发送或老格式，用 id 映射并打 `(?)` 标记

**local_type 复合类型**：形如 `244813135921 = (57<<32)|49` 的是带标志位的子类型（多数是压缩的链接/文件；`(n<<32)|1` 是压缩文本，数量很少）。压缩内容以 zstd magic `28 b5 2f fd` 开头。

### 1.5.2 必须做的第二步：zstd 解码修复（2026-09-23 实测，不做等于白导）

**症状**：导出文件里大量行长这样，正文是一坨 Python bytes repr：

```
2023-04-30 13:54:56 | <成员A>(?): b"(\xb5/\xfd`\xa1\x00\r\x0b\x00\x06UO<@\x87X\x07...
```

`(\xb5/\xfd` = zstd 帧魔数 `28 B5 2F FD`。原因：部分 `local_type=1` 的消息，其 `message_content`
**整体是 zstd 压缩后存库的**。导出脚本 `str(content)` 直接把 bytes 的 repr 写进了文本。
**这不是数据损坏，是少了一个解压步骤。**

**覆盖面极大，且和分片 bug 叠加**：老分片里压缩消息比例高得多。15 群实测 **大量行 / 全量行 = 38.9%**，
其中个别群（示例中压缩占比最高的一例）可达 **94% 量级**（绝大多数行）。旧版只读 m0 所以只发现少量，一度以为「量不大」。

```powershell
# 修复（生成独立副本，绝不改原始导出；在仓库根执行）
node skills\qq-wechat-trace\scripts\wx_fix_zstd.mjs
python skills\qq-wechat-trace\scripts\wx_verify_fix.py
```

- 输出：`<home>/export_wx_<日期>_decoded/wx_<群号>.txt` + `_senders.tsv`
- **修复顺手交出真发送者**：解压后的载荷开头内嵌发送者账号，共 3 种形态
  （`wxid_xxx:`、`数字@openim:`、其它自定义 wxid 前缀等形态），
  全部剥掉并记入 `_senders.tsv`。**原始导出里看不到这些账号**，共实测 **数万级**，做人物画像很有用。
- 对账标准：改动行 = 解码数、残留压缩串 = 0、非压缩行被误改 = 0、行数 = 原 +1（元信息块多一行"修复说明"）

**⚠️ 最容易踩的坑：Python repr 的引号会变。** 内容里含单引号 `'` 时，`repr(bytes)` 会自动改用**双引号** `b"..."`。
旧工具 `fix_wx_zstd.mjs` 第 61/62 行只匹配 `: b'` 和 `endsWith("'")`，**双引号形式全部漏掉**。
本次实测 **千条级是双引号形式**——用旧工具跑，这 千条级会以乱码永留文件里。
v2 (`fix_wx_zstd_v2.mjs`) 两种引号都认，且遇到未知转义序列直接抛错而不是静默写错字节。

**修复后仍存在的限制**（写进了 `_修复说明`，别当准信）：
1. 行首的 `发送者(?)` 仍是按 `real_sender_id` 推测的名字，**不是真名**；真账号只在 `_senders.tsv` 里。
2. `@openim` 发送者只有 id 没有昵称。
3. "非文本消息"里大量未识别类型码（`244813135921:5801` 这类）内容仍缺失——那是类型映射表不全，另一个问题。

### 1.5.3 换环境 / 换机器 / 挪目录时要改什么（2026-09-23 实测）

这三个脚本**放在哪里都能跑**（路径写死在脚本内部，与脚本位置无关），但换机器、挪数据目录、
换账号时**必须改下面几处**，否则报错长相很容易被误判成"数据库坏了"或"密钥错了"。

**① Python 解释器——最要紧，先看这个**

本机 PATH 上有 4 个解释器，只有 2 个装了 `sqlcipher3`：

| 解释器 | 版本 | sqlcipher3 |
|---|---|---|
| `C:\Python314\python.exe` | 3.14.0 | ✅ 有（0.6.2 / SQLite 3.50.4，装在 `%APPDATA%\Python\Python314\site-packages`） |
| `…\Programs\Python\Python313\python.exe` | 3.13.12 | ✅ 有 |
| `…\Programs\Python\Python312\python.exe` | 3.12.10 | ❌ 无 |
| `<其它项目>\venv\Scripts\python.exe` | 3.11.x 示例 | ❌ 无 sqlcipher3 时勿用 |

`python` 现在解析到第一个纯粹是 PATH 顺序。**命令一律写死解释器，别依赖 PATH、别用 `py`**：


## 2. 避坑清单（动手前 30 秒过一遍）

| # | 坑 | 解法 |
|---|---|---|
| 1 | **`PRAGMA key` 的引号** | `x'...'` 含单引号，外层必须双引号：`PRAGMA key = "x'...'"`；用单引号报 `unrecognized token` |
| 2 | **`cipher_page_size=4096` 必须在 `key` 之前** | 与 QQ 同一教训，顺序错 HMAC 失败 |
| 3 | **备份别用 robocopy** | 整目录 24 万个小文件会拖死；用 `tar -cf`（db_storage 3GB 实测 3.2 秒） |
| 4 | **密钥懒加载** | 没点开过的库密钥不在内存里，表现为匹配后“未覆盖”→ 点开聊天再扫 |
| 5 | **别想从 WeFlow 配置直提密钥** | DPAPI 外还包着 native protection，外部解不开；要裸密钥直接扫内存 |
| 6 | 解出的库要在**完整文件**上验证 | 截断文件报 malformed，不是密钥错 |
| 7 | tar 是快照 | 要新数据：关微信 → 重 tar（3 秒），密钥不变 |
| 8 | **发送者张冠李戴** | 群消息 94% 自带 `wxid:\n` 前缀，发送者以此为准；real_sender_id→contact.id 映射实测不可靠 |
| 9 | 内容开头是二进制 `(\xb5/\xfd` | zstd 压缩内容（magic 28 b5 2f fd）。**2026-09-22 时这里写的是「少量、未解压」，是错的**：实测抽样多群里约 **38.9%** 的行中招，单群最高可达 **94% 量级**。必须解码，见 1.5.2 |
| 10 | 某群搜不到 Msg 表 | 该群会话没在本机加载过（懒加载）；微信开着点开它再扫/再查 |
| 11 | **分片漏数据（最严重，2026-09-23 才发现）** | 同一群的 `Msg_<hash>` 表**同时存在于多个 `message_N.db`**，按时间分片（索引越大越老）。旧工具"首次命中即锁定"只读第一个库，15 个群只导出 20%。必须合并全部分片，用 `wx_export_shards.py`；对账方法见 1.5.1 |
| 12 | **zstd 压缩消息没解压** | 部分 `local_type=1` 的 `message_content` 整体是 zstd 压缩的，`str(content)` 会把 bytes repr 写进文本（表现为 `b"(\xb5/\xfd...`）。抽样多群里约 **38.9%** 行中招，单群最高 **94% 量级**。必须跑 `fix_wx_zstd_v2.mjs` 修复，见 1.5.2 |
| 13 | **Python repr 引号会变（修复工具的头号坑）** | 内容含单引号时 `repr(bytes)` 改用双引号 `b"..."`。旧修复工具只匹配单引号，本次实测 **千条级双引号形式**会被整批漏掉。必须用 v2 |
| 14 | **脚本硬编码路径 + PATH 上有 4 个 Python** | 导出/修复脚本的数据路径写死在内部，换机器或挪目录必须改（见 1.5.3 逐行清单）；命令要写死 `C:\Python314\python.exe`，PATH 顺序一变就会落到没有 sqlcipher3 的解释器上，报错会被误判成数据库/密钥问题 |

## 3. 资产重建（压缩版，细节见附录 E）

### 3.1 重新备份

## 附录 D：长期使用注意（一劳永逸之后的维护）

| 事项 | 说明 | 动作 |
|---|---|---|
| **数据时效** | tar 是快照，之后的新消息不在里面 | 要最新数据：关微信 → 重新 tar（3 秒）→ 密钥不变直接解 |
| **新分片库** | message_6 写满会开 message_7，新库盐/钥不在 map 里 | 微信开着点开一个该库的聊天 → 重跑扫描+匹配（不用重启，一分钟） |
| **密钥失效** | 仅重装微信/换账号失效（跨重启、跨升级不变，社区实测） | 重扫内存即可（密钥粘性，扫到即得） |
| **媒体未解密** | 图片/视频/语音（.dat 文件）还没做解密 | 要做时参考 wechat-db-decrypt / chatlog 的媒体解密实现 |
| **无名字的群** | contact 表里 27 个群没有名字（未加载过） | 在微信里点开这些群，再查 contact.db 即补上 |
| **与 WeFlow 的关系** | WeFlow 可继续作日常查看器；数据管线已完全自主 | WeFlow 被微信升级弄挂也不影响本地路线 |
| **历史完整度** | 实测：`message_0.db` 的数据起点约 **2026-04-07**（本机 PC 端库建立时间），`message_1/2.db` 存有更早数据（如 2024-06）。某群文本少≠群冷，可能是 PC 端未同步全量历史 | 要完整老历史：手机端做“聊天记录迁移”到本机，或接受 PC 端范围；导出文件头部的“最早时间/非文本计数”可用于判断 |
| **分片必须合并（2026-09-23 新增）** | 同一群的消息按时间分布在 m0~m6 多个库，只读一个库最多丢 80%。旧版 15 群导出实际只有 20%（29,257 / 147,044 条） | 一律用 `wx_export_shards.py` 合并全分片；每个群跑完核对 `分片来源` 求和 == `文本消息数` |
| **zstd 必须解码（2026-09-23 新增）** | 压缩消息在老分片里比例更高，和分片 bug 叠加后抽样多群约 **38.9%** 行中招（单群最高 **94% 量级**）。只读 m0 时只看见少量，容易低估 | 导出后必须跑 `fix_wx_zstd_v2.mjs` + `verify_wx_fix_v2.py`；用旧版 v1 工具会漏掉双引号形式（实测千条级） |
| **发送者(?)不是真名** | 压缩消息解出的真实 wxid 只落在 `_senders.tsv`，行首显示名仍是按 `real_sender_id` 推测的 | 做人物画像/统计时必须 join `_senders.tsv`，别拿行首 `(?)` 名字当准信 |
| **PC 端的历史洞** | PC 微信**没有云端同步**，关机期间的消息收不到（登录时只回收最近约 3 天）。2026-09-23 实测：<群名>/<群名> 等群在 2026-08-05、08-06、08-19、08-20 有洞，手机端迁移后补齐 | 每 3 天登录一次 PC 微信可减少洞；要补洞：手机端“聊天记录迁移与备份→迁移”，**时间范围务必选“全部时间范围”**；迁移是拷贝不是搬移，手机端不丢 |
| **云端 72h 规则（官方原文）** | 《WeChat 隐私政策》：“聊天信息会在发送至接收者设备后不久从我们的服务器中删除，并且在任何情况下，都会在您发送这些信息 72 小时后删除。图片、音频、视频和文件等聊天媒体会在您发送它们 120 小时后……自动删除”——**任一设备在消息发出后 72h 内没接过，这条就永久消失**。实测 4 个洞（98/53/47/129 天，全在 2025-09~2026-08，当时手机电脑同时离线） | 洞补不了，只能预防：至少一台设备 72h 内上线接消息 |

| **活库比旧快照多** | 2026-09-23 14:57 实测 QQ 活库比 09-21 备份大 80 MB（24,376,787,968 vs 24,292,705,280 字节） | QQ/微信的活库都在持续增长，旧导出是快照。要最新数据：关客户端（确保无 wal/shm）→ 重备 → 重导 |

## 附录 E：完整操作实录（2026-09-21，含走过的弯路）

> 真实时序。保留弯路是因为——下次遇到同样现象能对号入座省时间。

### 阶段 0：起点
- 微信 4.1.8.x 运行中；WeFlow 等第三方查看器与本导出管线独立，可不装

### 阶段 1：路线 A——WeFlow 一条龙（20 分钟）
1. 读源码 `KeyService.ts`：机制 = koffi 加载 `wx_key.dll` → `InitializeHook(微信PID)` → 轮询 `PollKeyData()` 拿 64 位 hex 密钥
2. 启动 WeFlow → 全自动提密钥+解密+开库（用户零操作）
3. 改 `WeFlow-config.json` 开 HTTP API → 重启 → health 通过
4. API 实测取到 **2022-03-31** 的消息——4 年半历史
- **结论**：日常查看/轻量导出，WeFlow 就是终点，无需自研

### 阶段 2：路线 B——裸密钥提取（约 1 小时）
1. **弯路 A**：想从 WeFlow 配置里直接解出缓存密钥——DPAPI 解 base64 失败（`数据无效`）。原因：WeFlow 在 safeStorage 外又包了一层 native protection（日志 `[bootstrap] native protection ok`），外部解不开
2. **拐点**：读 ax0x 博客，拿到关键情报——WCDB 把派生好的裸密钥连盐一起缓存在进程内存，形态是 `x'<64位hex密钥><32位hex盐>'`
3. **正解**：写内存扫描器扫全部 Weixin.exe 进程（ASCII + UTF-16LE 两种形态都抓）→ **34 把密钥**
4. 盐匹配：读每个 .db 文件头 16 字节 = 该库盐 → 自动配对 → **24/25 库覆盖**（唯一漏 `migrate\unspportmsg.db` 迁移遗留库，无关）
5. 验证：bizchat.db 打开成功（6 张表）

### 阶段 3：备份与导出测试
1. **备份弯路**：robocopy 整目录拷贝——24.37GB/24.8 万文件（媒体小文件拖死速度），20 分钟只拷了 9GB，杀掉
2. **正解**：分层后发现 db_storage 只要 3GB/117 文件 → `tar` **3.2 秒完成**，WAL/shm 天然包含
3. 清理 robocopy 残渣（14.37GB/21 万文件）：Python rmtree，个别 .dat 只读报 WinError 5 → `onexc` chmod 后重试清掉
4. 导出测试：从 tar 提取 message_6.db → 密钥解密 → **发现文本消息的 message_content 直接是明文**（无需 protobuf），记录直读至 **2021-04-02**
