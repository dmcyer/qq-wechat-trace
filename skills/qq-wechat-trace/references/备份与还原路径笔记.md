## 1. QQ 聊天数据库备份（本次制作）

| 项 | 值 |
|---|---|
| 备份目录 | `D:\qq_db_backup_<日期>\` |
| 内容 | `nt_msg.db`（约 22.6 GB）、`nt_msg.db-first.material`（16KB）、`nt_msg.db-last.material`（16KB） |
| 快照时间 | 本次制作；拷贝前源库已零写入、WAL 已 checkpoint（WAL 已 checkpoint 合并），属完整一致快照，无撕裂 |
| 校验特征 | 文件头含 `QQ_NT DB` + 库自带的 rand 串（与原库一致） |

### 原始路径（还原目标）

| 备份文件 | 还原到 |
|---|---|
| `nt_msg.db` | `<QQ_DATA_ROOT>\<QQ_UIN>\nt_qq\nt_db\nt_msg.db` |
| `nt_msg.db-first.material` | `<QQ_DATA_ROOT>\<QQ_UIN>\nt_qq\nt_db\nt_msg.db-first.material` |
| `nt_msg.db-last.material` | `<QQ_DATA_ROOT>\<QQ_UIN>\nt_qq\nt_db\nt_msg.db-last.material` |

### 还原步骤

1. **完全关闭 QQ**：任务管理器结束所有 `QQ.exe`；若 NapCat/QCE 在运行，一并结束 `NapCatWinBootMain.exe`（文件被锁时无法覆盖）
2. 把现有的 `nt_msg.db` **改名**（不要删除），例如 `nt_msg.db.broken-<日期>`
3. 还原命令（QQ 关闭后执行）：

```powershell
robocopy "D:\qq_db_backup_<日期>" "<QQ_DATA_ROOT>\<QQ_UIN>\nt_qq\nt_db" nt_msg.db nt_msg.db-first.material nt_msg.db-last.material /Z /R:2 /W:5
```

4. 校验：**文件大小与备份时一致**；**文件头 rand 串与备份时一致**（两处都别改，改了 QQ 认不出库）
5. 重启 QQ，抽查历史消息是否正常加载

### 注意事项

- 还原会丢失快照时刻之后的新消息——这是用时间换安全
- 备份与原库同在 D 盘：防“逻辑损坏”，不防硬盘物理故障
- 想重新备份时（QQ 关闭时执行最干净）：

```powershell
robocopy "<QQ_DATA_ROOT>\<QQ_UIN>\nt_qq\nt_db" "D:\qq_db_backup_<日期>" nt_msg.db nt_msg.db-first.material nt_msg.db-last.material /Z /R:2 /W:5
```

## 5. QQ 本地数据库解密（2026-09-21 打通）

### 5.1 成果与要素

| 项 | 内容 |
|---|---|
| 密钥 | **16 位**，官方 ps1 从 R8 捕获；存于 `keys/QQ_DB_KEY_<QQ号>.txt`（**末尾换行须 trim**） |
| 源库 | `D:\qq_db_backup_<日期>\nt_msg.db`（约 24 GB 完整备份，原库只读未动） |
| 解密方法 | 剥 1024 字节 QQ_NT 头 → sqlcipher3 打开。**PRAGMA 顺序是关键：`cipher_page_size=4096` 必须在 `key` 之前**，然后 `kdf_iter=4000`、`cipher_hmac_algorithm=HMAC_SHA1`、`cipher_kdf_algorithm=PBKDF2_HMAC_SHA512` |
| 成果 | group_msg_table **约千万级 条群消息**、c2c_msg_table 数万级 条私聊、group_at_me_msg 约万级 条——本地库是 API 路线（10 万条/6 晚）的 **240 倍**，且覆盖全部群 |
| 权威工具 | 提密钥：QQBackup/qq-win-db-key（windows_ntqq_get_key.ps1）；解密导出：QQBackup/nt_msg_db_util（1.decrypt.py / 2.slim.py / 3.export.py）；文档 qqbackup.github.io/QQDecrypt |
| 中间产物 | `<home>/work/nt_msg_clear_<QQ号>.db`（剥头后的约 24 GB，可直接 sqlcipher 打开） |

### 5.2 避坑清单（按踩坑代价排序）

1. **PRAGMA 顺序错是最大坑**：`cipher_page_size=4096` 必须在 `PRAGMA key` **之前**，之后依次 `kdf_iter=4000` → `hmac=HMAC_SHA1` → `kdf=PBKDF2_HMAC_SHA512`。key 放第一位 → 永远 `hmac check failed`。该顺序写在 nt_msg_db_util/1.decrypt.py 的 docstring 里。
2. **先读官方实现再动手**：本次为盲猜参数浪费约 3 小时（iter/prf/hmac/reserve/iv 排列组合全试一遍），答案一直在官方脚本注释里。**凡有官方工具/文档的任务，先把源码或文档读一遍再写代码。**
3. **截断文件会误报 malformed**：用 64MB 探针测试报 `database disk image is malformed`，误以为参数仍错，其实参数已对（HMAC 已过），只是文件不完整。验证解密必须在完整文件上进行。
4. **提密钥**：优先 `scripts/fetch_qq_key.ps1`（拉 QQBackup 官方 ps1，登录一次）。勿自研 Frida；若调试，R8 = Frida `args[2]`，readCString 过滤会漏密钥。
7. **密钥文件换行坑**：QQ_DB_KEY.txt 由 write 工具生成，末尾带 \n，拼进 PRAGMA 前必须 trim。

### 5.3 下次加速路径（照做即可）

1. 备份：QQ 关闭时 robocopy 整个账号 nt_qq 目录（含 nt_db）到 `D:\qq_db_backup_<日期>\`
2. 提密钥：跑官方 ps1（`irm https://raw.githubusercontent.com/QQBackup/qq-win-db-key/master/scripts/windows/ntqq/windows_ntqq_get_key.ps1 | iex`），用户登录一次，拿 16 位密钥
3. 解密：`pip install sqlcipher3`，剥 1024 字节头，按 5.1 的 PRAGMA 顺序打开**完整文件**
4. 导出：直接用 nt_msg_db_util 的 3.export.py，或自写脚本（group_msg_table：`40050`=时间戳 / `40021`=群UID / `40020`=发送者UID / `40033`=发送者QQ / `40800`=protobuf 内容；`nt_uid_mapping_table` 做 UID→身份映射）

### 5.4 微信侧的对应结论

- 微信本地库路线 = **WeFlow 一条龙**（已装 6.2.0，2026-09-21 实测可读 4.1.8），无需自研；HTTP API 可开（127.0.0.1:5031，token 自定，端点 /api/v1/messages?talker=&start=&end=&limit）
- 微信密钥被 DPAPI + native protection 双层包裹，外部无法提取——但也不需要提，WeFlow 自己管
- 微信 .material 文件 = 盐(16B) + 被包裹的密钥材料，离线解不开（与 QQ 的 .material 同源不同包装）

## 6. 微信裸密钥提取（2026-09-21 打通，第二条本地路线）

### 6.1 成果

| 项 | 内容 |
|---|---|
| 密钥数量 | **34 把**（扫 Weixin.exe 内存所得），按盐匹配覆盖 **24/25 个数据库**（唯一未覆盖：`migrate\unspportmsg.db`，迁移遗留库，无关） |
| 密钥形态 | `x'<64位hex密钥><32位hex盐>'`（WCDB 缓存的 SQLCipher 裸密钥，**连盐一起给**） |
| 密钥映射表 | `keys/wx_db_key_map.json`（库路径 → key+salt，24 条） |
| 原始扫描结果 | `scripts/wechat_keys.json`（34 把全量） |
| 解密验证 | ✅ 已实测打开 bizchat.db（6 张表） |
| 覆盖范围 | message_0~6、biz_message_0/1、media_0、message_fts、message_resource、contact、session、favorite、emoticon、sns、general、hardlink、head_image、solitaire、bizchat 全部 |

### 6.2 方法（下次照做）

1. 保持微信运行；**先把想导出的群/聊天点开一遍**（WCDB 懒加载，只有打开过的库密钥才进内存；密钥在进程内存里累积，**不用重启**，扫一遍→点开漏的→再扫，2-3 轮全覆盖）
2. 扫内存抓 `x'<64hex><32hex>'`（ASCII + UTF-16LE 两种形态都要抓）→ `wx_mem_scan.py`
3. 读每个 .db 文件头 16 字节 = 该库盐 → 和密钥配对 → `match_salts.py`
4. 解密：**先 `PRAGMA cipher_page_size = 4096;` 再 `PRAGMA key = "x'<key><salt>'";`**（外层双引号！裸密钥模式无需 kdf_iter，HMAC 用默认 SHA512 即可——实测一把过）

### 6.3 避坑

- **SQL 引号坑**：`x'...'` 含单引号，PRAGMA 外层必须用双引号：`PRAGMA key = "x'...'"`，用单引号会报 `unrecognized token`
- **懒加载**：没点开过的群，其库密钥不在内存里——表现为匹配后该库"未覆盖"，点开任意聊天再扫即可
- **密钥粘性**：跨重启、跨升级不变（社区实测），提取一次永久可用；只有重装微信/换账号才需重提
- 扫描是纯本地内存读，零网络请求、不 hook 不注入，微信无感知

### 6.4 意义

拿到裸密钥后，微信数据解密**不再依赖 WeFlow、也不再需要微信运行**——与 QQ 路线殊途同归（备份库文件 + 密钥 → 离线永久可解）。WeFlow 仍可作日常查看器，但数据管线已完全自主。
